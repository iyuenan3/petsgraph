## 画布安全边界不足导致尾巴被生成视频裁断 · 2026-08-09

- 现象: `stand-right-loop` 的首个长循环区间后段尾巴碰到左边界，缩短后可保留完整循环；随后 `stand-right-to-walk-right` 第 1 次生成在多个起步区间把尾尖直接裁在左边界。缩略接触表初看动作连续，但透明外圈 alpha 检查暴露多帧 `x=0`。裁切发生前的连续帧仍处于站立准备阶段，无法自然接入已批准走路循环。
- 根因: 首尾锚点中的宠物占画布过满，只按静态包围盒检查，没有为起步时尾巴向左摆动预留运动包络；接触表缩小后又弱化了边缘裁切的可见性。
- 结论/避免: 首尾帧提交前同时检查静态包围盒与动作运动包络，可见主体不得进入外圈 8px。尾巴摆动动作需要更大的左右安全边界。任何 `alpha x=0` 或 `x=canvasWidth-1` 都触发逐帧人工复核。已经被画布裁断的尾巴不能通过整体平移、抠图或补画进入正式素材，只能拒绝母片并以缩小端点主体作为下一次单变量尝试。

## 离散帧与衔接指标未发现正常速度下的后脚滑步 · 2026-08-09

- 现象: `stand-right-to-walk-right` 第 2 次通过了外圈 alpha、逐帧边距、主体中心漂移和两处衔接检查，接触表中的四肢姿态也没有明显断裂。用户观看完整动作链时仍在第 4 到第 5 秒发现后腿滑了一步，对应起步边内部约 1.6 到 2.6 秒、帧 39 到 63。
- 根因: 接触表每隔 2 到 4 帧抽样，只能显示离散姿态；主体中心和衔接指标只衡量整体位置变化，不能判断承重脚在连续帧中是否出现不符合步态的接地滑动。机械检查覆盖了画布与切换，却没有覆盖脚掌接触阶段的时序自然度。
- 结论/避免: 走路、跑步和所有步态过渡必须额外观看正常速度与必要的慢速连续视频，重点检查每只脚的抬起、摆动、落地、承重和离地。机械指标与接触表只用于定位区间，不得写成步态自然度通过。若用户指出时间点，应映射到动作内部帧区间，并在下一次受控尝试中只针对该步态阶段改变约束。

## 严格首尾帧不能同时混用参考媒体 · 2026-08-09

- 现象: `run-right-loop` 第 1 次同时提交同一首尾帧、身份参考图和动作参考视频，在任务创建前收到 `InvalidParameter`。第 2 次移除身份参考图但保留动作参考视频，仍在任务创建前被拒绝。两次均未产生任务 ID 或生成消耗。
- 根因: 当前 Seedance 接口不允许双首尾帧与参考图片、参考视频或参考音频同时存在；错误文案在逐步移除参考角色后才完整暴露这条组合约束。
- 结论/避免: 需要严格首尾相位时使用纯首尾帧模式；需要多模态身份或动作参考时不能再依赖双首尾帧闭环。提交器在上传大文件或创建任务前应做角色组合校验，失败尝试仍保留请求摘要、错误码与临时对象清理回执。

## 青幕通道放大把压缩波动误判为主体 · 2026-08-09

- 现象: `run-right-loop` 初次机械分析在纯青背景区域出现大块低透明度残影，接触表像是背景污染；检查原始帧后确认这些区域只是有损视频压缩造成的青色轻微波动，不是真实宠物或生成残留。
- 根因: 首版色键直接放大通道差，对压缩后不再完全一致的青幕像素过敏，又缺少与主体连通性和颜色距离的联合约束。
- 结论/避免: 青幕母片先从画面边界估计背景中位色，再结合归一化通道差、颜色距离、主体连通分量和 alpha 下限生成蒙版，并同时在浅底和深底复核。色键算法发现规则性大块残影时，先检查工具是否放大压缩噪声，不能直接把它归因于生成模型。

## 分段通过未暴露整链画布缩放不一致 · 2026-08-09

- 现象: 站走与停步评审链使用约 0.868 的走路归一化，走跑与跑走评审链使用约 0.8451 的走路归一化。每条边分别连接相邻循环时都能通过，但首次组装七段真实运行时链后发现两组基准相差约 2.7%，直接拼接会在进入走跑链时产生体型跳变。
- 根因: 图边验收验证了局部端点和相邻循环，没有维护宠物级唯一画布变换，也没有在所有通过单元完成后编译一次全链检查全局尺度。
- 结论/避免: 每只宠物在首条移动链阶段就锁定全局中心、地面和尺度基准。历史已通过边允许对整段做同一确定性缩放和重定位，但变换后的完整真实窗口链必须重新人工验收。以后每条边的输入清单必须引用宠物级规范化版本，不能只引用局部评审链版本。

## 复用通用模拟速度导致真实宠物慢走过快 · 2026-08-09

- 现象: 首个 AppKit 原型沿用 petsdesk 的 48 pt/s 走路与 115 pt/s 跑步校准。窗口和动画同步工作正常，但用户在真实桌面观看后明确判断走路移动太快。
- 根因: petsdesk 的速度是通用行为模拟参数，不是从五百当前走路素材和显示尺寸人工校准的 root motion。工程上的速度比满足要求，不代表视觉上像这只宠物的步幅。
- 结论/避免: 速度参考只能作为首个候选，必须在真实显示高度和原生窗口中逐只宠物验收。五百第二版走路降为 30 pt/s，跑步暂留 115 pt/s；通过前保持 `provisional`，不得因测试满足跑步快于走路就升级为运行时通过。

## Desktop File Provider 路径的目录枚举偶发漏片段 · 2026-08-09

- 现象: 同一份已拒绝历史包中，shell 能看到 7 个片段 JSON，Swift `FileManager.contentsOfDirectory` 一次只返回 6 个，导致站立节点被误报为引用未知循环。文件可按精确路径读取，包内 JSON、字节数和 SHA-256 均未损坏。该路径带有 File Provider 目录属性。
- 根因: 运行时把目录枚举结果当作动作集合事实源，在 File Provider 管理路径出现可见结果不完整时放大为包校验失败。现有证据只能确认目录枚举与精确寻址结果不一致，不能进一步断言 File Provider 的内部根因。
- 结论/避免: 动作图是必需片段集合的唯一事实源。加载器从节点 `loopClip` 和边 `clip` 推导 ID，再按 `clips/<clip-id>.json` 显式读取并验证声明 ID，不依赖目录枚举。修复后当前候选与历史包均读取 7 个片段并通过 519 文件完整性校验。

## 点号临时构建目录产生 hidden 素材包 · 2026-08-09

- 现象: 旧睡眠实验包的一条 clip JSON 带 `UF_HIDDEN`，旧右向包的根目录也带相同标记。文件内容和 SHA-256 可以正确，但依赖跳过隐藏文件的加载方式会漏读。新包改用非点号临时目录后，根目录和 800 个清单文件的 hidden 标记检查为零。
- 根因: 旧编译器在 File Provider 管理的项目目录内使用点号开头的临时构建目录，再把该目录重命名为正式包。观察证据确认 hidden 标记由这条构建路径产生或继承，无法仅凭现象断言 File Provider 的更深内部机制。
- 结论/避免: 临时包目录不用点号前缀，编译器在安装前后递归检查 `UF_HIDDEN`，发现任一标记就失败并恢复旧版本。加载器显式拒绝 hidden 必需文件，不让异常包静默进入运行时，也不要求用户手动执行 `chflags`。

## CommandLineTools 缺少两套 Swift 测试模块 · 2026-08-09

- 现象: 当前 `xcode-select` 指向 `/Library/Developer/CommandLineTools`。同一 Swift 6.3.3 版本下，使用 `Testing` 报 `no such module 'Testing'`，迁移到 XCTest 后裸 `swift test` 又报 `no such module 'XCTest'`。完整 Xcode 26.6 下 XCTest 构建并运行 10 项测试全部通过。
- 根因: 当前 CommandLineTools 安装不包含项目测试目标需要的 `Testing` 或 `XCTest` 平台模块，版本字符串相同不能证明测试框架可用。
- 结论/避免: 项目测试使用 XCTest，并通过 `tools/test-swift.sh` 显式设置完整 Xcode 的 `DEVELOPER_DIR` 与仓库内模块缓存。不修改用户全局 `xcode-select`，也不把只有 `swift build` 成功写成测试基线通过。

## 把 provider 终端帧一律删除会破坏步态衔接 · 2026-08-09

- 现象: 早期过渡可以排除 provider 重复的终端端点后直接进入目标循环，但坐姿到右向行走的通过版本必须保留终端帧作为已批准走路第 22 相位，再从循环第 23 相位继续。若沿用统一删除规则，边结束时还没有到达足够接近的走路接触相位。
- 根因: 把某些母片中的重复终端帧误当成生成接口的固定行为，没有逐条边比较倒数帧、严格端点和目标循环相位。
- 结论/避免: 终端帧的保留或排除是每条边的确定性切分决策。必须比较端点相似度、承重姿态和后续相位，记录边的最终源帧与目标循环下一相位，并在完整链中验收，不能套用全局删除规则。

## 理论帧率边界与清单时长舍入不完全相同 · 2026-08-09

- 现象: 24 FPS 片段在测试中用理论值 `1000 / 24` 推导边界时，累计浮点值可能仍落在上一帧；包内每帧实际声明 `durationMs=41.666667`，二者累积后存在微小差异。
- 根因: 运行时以素材清单声明的逐帧时长为事实源，测试却另行从名义 FPS 重建时间轴。两个近似值在片段边界放大舍入差异，使断言测试了另一套时钟。
- 结论/避免: 时间轴测试从已加载帧的 `durationMs` 累加采样，不用名义 FPS 重算边界。名义 FPS 只用于批准配方一致性校验，不能覆盖运行时清单的实际时长。

## 真实桌面录屏可能把无关私密内容带入评审材料 · 2026-08-09

- 现象: 直接录制真实桌面能证明透明窗口层级和位移，但也会把与宠物无关的桌面内容一并带入视频，不适合直接作为可分享评审材料。
- 根因: 运行时验收需要真实 AppKit 窗口，录制范围却没有把产品证据与用户桌面背景的隐私边界分开。
- 结论/避免: 评审录屏仍使用真实原生窗口和真实坐标，但先布置受控中性背景并确认窗口层级、尺寸与位置不变。原始全桌面证据只在本地受控目录保留，不默认进入 Git、公开文档或可分享素材包。

## 工程能力被误当成首发产品范围 · 2026-08-10

- 现象: 右向和左向走跑、root motion、点击目的地、全局鼠标监听和边界处理不断扩大后，运行时多次出现点击不明显、强制跑步无效、窗口消失、左向画面异常和移动中错误记录点击等问题。用户同时发现，只看五百睡觉和更换睡姿已经能提供最舒服的陪伴感。
- 根因: Phase 0 为验证最难技术风险选择走跑链是合理的，但文档把“优先验证的工程能力”长期当成“首发必须交付的产品能力”，没有在核心价值被真实观察推翻后及时重新划定 Target 与 As-built。
- 结论/避免: 技术证据和产品范围分开记录。已验证走跑能力与素材继续保留，但首个产品只交付安静睡眠、点击坐立、随机换姿、枕头场景和拖动。以后每个新动作先回答它是否提高长期陪伴感；不能只因为已经实现或素材已经生成就进入默认行为。
