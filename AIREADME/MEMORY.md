## 画布安全边界不足导致尾巴被生成视频裁断 · 2026-08-09

- 现象: `stand-right-loop` 的首个长循环区间后段尾巴碰到左边界，缩短后可保留完整循环；随后 `stand-right-to-walk-right` 第 1 次生成在多个起步区间把尾尖直接裁在左边界。缩略接触表初看动作连续，但透明外圈 alpha 检查暴露多帧 `x=0`。裁切发生前的连续帧仍处于站立准备阶段，无法自然接入已批准走路循环。
- 根因: 首尾锚点中的宠物占画布过满，只按静态包围盒检查，没有为起步时尾巴向左摆动预留运动包络；接触表缩小后又弱化了边缘裁切的可见性。
- 结论/避免: 首尾帧提交前同时检查静态包围盒与动作运动包络，可见主体不得进入外圈 8px。尾巴摆动动作需要更大的左右安全边界。任何 `alpha x=0` 或 `x=canvasWidth-1` 都触发逐帧人工复核。已经被画布裁断的尾巴不能通过整体平移、抠图或补画进入正式素材，只能拒绝母片并以缩小端点主体作为下一次单变量尝试。

## 离散帧与衔接指标未发现正常速度下的后脚滑步 · 2026-08-09

- 现象: `stand-right-to-walk-right` 第 2 次通过了外圈 alpha、逐帧边距、主体中心漂移和两处衔接检查，接触表中的四肢姿态也没有明显断裂。用户观看完整动作链时仍在第 4 到第 5 秒发现后腿滑了一步，对应起步边内部约 1.6 到 2.6 秒、帧 39 到 63。
- 根因: 接触表每隔 2 到 4 帧抽样，只能显示离散姿态；主体中心和衔接指标只衡量整体位置变化，不能判断承重脚在连续帧中是否出现不符合步态的接地滑动。机械检查覆盖了画布与切换，却没有覆盖脚掌接触阶段的时序自然度。
- 结论/避免: 走路、跑步和所有步态过渡必须额外观看正常速度与必要的慢速连续视频，重点检查每只脚的抬起、摆动、落地、承重和离地。机械指标与接触表只用于定位区间，不得写成步态自然度通过。若用户指出时间点，应映射到动作内部帧区间，并在下一次受控尝试中只针对该步态阶段改变约束。

## 严格首尾帧不能同时混用参考媒体 · 2026-08-09

- 现象: `run-right-loop` 第 1 次同时提交同一首尾帧、身份参考图和动作参考视频，在任务创建前收到 `InvalidParameter`。第 2 次移除身份参考图但保留动作参考视频，仍在任务创建前被拒绝。两次均未产生任务 ID 或生成消耗。
- 根因: 当前 Seedance 接口不允许双首尾帧与参考图片、参考视频或参考音频同时存在；错误文案在逐步移除参考角色后才完整暴露这条组合约束。
- 结论/避免: 需要严格首尾相位时使用纯首尾帧模式；需要多模态身份或动作参考时不能再依赖双首尾帧闭环。提交器在上传大文件或创建任务前应做角色组合校验，失败尝试仍保留请求摘要、错误码与临时对象清理回执。

## 青幕通道放大把压缩波动误判为主体 · 2026-08-09

- 现象: `run-right-loop` 初次机械分析在纯青背景区域出现大块低透明度残影，接触表像是背景污染；检查原始帧后确认这些区域只是有损视频压缩造成的青色轻微波动，不是真实宠物或生成残留。
- 根因: 首版色键直接放大通道差，对压缩后不再完全一致的青幕像素过敏，又缺少与主体连通性和颜色距离的联合约束。
- 结论/避免: 青幕母片先从画面边界估计背景中位色，再结合归一化通道差、颜色距离、主体连通分量和 alpha 下限生成蒙版，并同时在浅底和深底复核。色键算法发现规则性大块残影时，先检查工具是否放大压缩噪声，不能直接把它归因于生成模型。

## 分段通过未暴露整链画布缩放不一致 · 2026-08-09

- 现象: 站走与停步评审链使用约 0.868 的走路归一化，走跑与跑走评审链使用约 0.8451 的走路归一化。每条边分别连接相邻循环时都能通过，但首次组装七段真实运行时链后发现两组基准相差约 2.7%，直接拼接会在进入走跑链时产生体型跳变。
- 根因: 图边验收验证了局部端点和相邻循环，没有维护宠物级唯一画布变换，也没有在所有通过单元完成后编译一次全链检查全局尺度。
- 结论/避免: 每只宠物在首条移动链阶段就锁定全局中心、地面和尺度基准。历史已通过边允许对整段做同一确定性缩放和重定位，但变换后的完整真实窗口链必须重新人工验收。以后每条边的输入清单必须引用宠物级规范化版本，不能只引用局部评审链版本。

## 复用通用模拟速度导致真实宠物慢走过快 · 2026-08-09

- 现象: 首个 AppKit 原型沿用 petsdesk 的 48 pt/s 走路与 115 pt/s 跑步校准。窗口和动画同步工作正常，但用户在真实桌面观看后明确判断走路移动太快。
- 根因: petsdesk 的速度是通用行为模拟参数，不是从五百当前走路素材和显示尺寸人工校准的 root motion。工程上的速度比满足要求，不代表视觉上像这只宠物的步幅。
- 结论/避免: 速度参考只能作为首个候选，必须在真实显示高度和原生窗口中逐只宠物验收。五百第二版走路降为 30 pt/s，跑步暂留 115 pt/s；通过前保持 `provisional`，不得因测试满足跑步快于走路就升级为运行时通过。

## Desktop File Provider 路径的目录枚举偶发漏片段 · 2026-08-09

- 现象: 同一份已拒绝历史包中，shell 能看到 7 个片段 JSON，Swift `FileManager.contentsOfDirectory` 一次只返回 6 个，导致站立节点被误报为引用未知循环。文件可按精确路径读取，包内 JSON、字节数和 SHA-256 均未损坏。该路径带有 File Provider 目录属性。
- 根因: 运行时把目录枚举结果当作动作集合事实源，在 File Provider 管理路径出现可见结果不完整时放大为包校验失败。现有证据只能确认目录枚举与精确寻址结果不一致，不能进一步断言 File Provider 的内部根因。
- 结论/避免: 动作图是必需片段集合的唯一事实源。加载器从节点 `loopClip` 和边 `clip` 推导 ID，再按 `clips/<clip-id>.json` 显式读取并验证声明 ID，不依赖目录枚举。修复后当前候选与历史包均读取 7 个片段并通过 519 文件完整性校验。

## 点号临时构建目录产生 hidden 素材包 · 2026-08-09

- 现象: 旧睡眠实验包的一条 clip JSON 带 `UF_HIDDEN`，旧右向包的根目录也带相同标记。文件内容和 SHA-256 可以正确，但依赖跳过隐藏文件的加载方式会漏读。新包改用非点号临时目录后，根目录和 800 个清单文件的 hidden 标记检查为零。
- 根因: 旧编译器在 File Provider 管理的项目目录内使用点号开头的临时构建目录，再把该目录重命名为正式包。观察证据确认 hidden 标记由这条构建路径产生或继承，无法仅凭现象断言 File Provider 的更深内部机制。
- 结论/避免: 临时包目录不用点号前缀，编译器在安装前后递归检查 `UF_HIDDEN`，发现任一标记就失败并恢复旧版本。加载器显式拒绝 hidden 必需文件，不让异常包静默进入运行时，也不要求用户手动执行 `chflags`。

## CommandLineTools 缺少两套 Swift 测试模块 · 2026-08-09

- 现象: 当前 `xcode-select` 指向 `/Library/Developer/CommandLineTools`。同一 Swift 6.3.3 版本下，使用 `Testing` 报 `no such module 'Testing'`，迁移到 XCTest 后裸 `swift test` 又报 `no such module 'XCTest'`。完整 Xcode 26.6 下 XCTest 构建并运行 10 项测试全部通过。
- 根因: 当前 CommandLineTools 安装不包含项目测试目标需要的 `Testing` 或 `XCTest` 平台模块，版本字符串相同不能证明测试框架可用。
- 结论/避免: 项目测试使用 XCTest，并通过 `tools/test-swift.sh` 显式设置完整 Xcode 的 `DEVELOPER_DIR` 与仓库内模块缓存。不修改用户全局 `xcode-select`，也不把只有 `swift build` 成功写成测试基线通过。

## 把 provider 终端帧一律删除会破坏步态衔接 · 2026-08-09

- 现象: 早期过渡可以排除 provider 重复的终端端点后直接进入目标循环，但坐姿到右向行走的通过版本必须保留终端帧作为已批准走路第 22 相位，再从循环第 23 相位继续。若沿用统一删除规则，边结束时还没有到达足够接近的走路接触相位。
- 根因: 把某些母片中的重复终端帧误当成生成接口的固定行为，没有逐条边比较倒数帧、严格端点和目标循环相位。
- 结论/避免: 终端帧的保留或排除是每条边的确定性切分决策。必须比较端点相似度、承重姿态和后续相位，记录边的最终源帧与目标循环下一相位，并在完整链中验收，不能套用全局删除规则。

## 理论帧率边界与清单时长舍入不完全相同 · 2026-08-09

- 现象: 24 FPS 片段在测试中用理论值 `1000 / 24` 推导边界时，累计浮点值可能仍落在上一帧；包内每帧实际声明 `durationMs=41.666667`，二者累积后存在微小差异。
- 根因: 运行时以素材清单声明的逐帧时长为事实源，测试却另行从名义 FPS 重建时间轴。两个近似值在片段边界放大舍入差异，使断言测试了另一套时钟。
- 结论/避免: 时间轴测试从已加载帧的 `durationMs` 累加采样，不用名义 FPS 重算边界。名义 FPS 只用于批准配方一致性校验，不能覆盖运行时清单的实际时长。

## 真实桌面录屏可能把无关私密内容带入评审材料 · 2026-08-09

- 现象: 直接录制真实桌面能证明透明窗口层级和位移，但也会把与宠物无关的桌面内容一并带入视频，不适合直接作为可分享评审材料。
- 根因: 运行时验收需要真实 AppKit 窗口，录制范围却没有把产品证据与用户桌面背景的隐私边界分开。
- 结论/避免: 评审录屏仍使用真实原生窗口和真实坐标，但先布置受控中性背景并确认窗口层级、尺寸与位置不变。原始全桌面证据只在本地受控目录保留，不默认进入 Git、公开文档或可分享素材包。

## 工程能力被误当成首发产品范围 · 2026-08-10

- 现象: 右向和左向走跑、root motion、点击目的地、全局鼠标监听和边界处理不断扩大后，运行时多次出现点击不明显、强制跑步无效、窗口消失、左向画面异常和移动中错误记录点击等问题。用户同时发现，只看五百睡觉和更换睡姿已经能提供最舒服的陪伴感。
- 根因: Phase 0 为验证最难技术风险选择走跑链是合理的，但文档把“优先验证的工程能力”长期当成“首发必须交付的产品能力”，没有在核心价值被真实观察推翻后及时重新划定 Target 与 As-built。
- 结论/避免: 技术证据和产品范围分开记录。已验证走跑能力与素材继续保留，但首个产品只交付安静睡眠、点击坐立、随机换姿、枕头场景和拖动。以后每个新动作先回答它是否提高长期陪伴感；不能只因为已经实现或素材已经生成就进入默认行为。

## 边框不可激活面板不能依赖辅助工具完成最终拖动验收 · 2026-08-10

- 现象: 自动化工具可以看到和点击透明宠物窗口，却对无边框、非激活 `NSPanel` 的拖动持续返回辅助功能未实现；全局 Space 快捷键与锁屏恢复也无法在不改变用户环境的情况下可靠代替人工操作。
- 根因: 运行时窗口刻意不激活、不抢焦点，并使用逐帧透明命中。辅助功能树没有提供等价的标准窗口拖动动作，工具能力边界与真实鼠标输入边界不同。
- 结论/避免: 自动化继续覆盖状态机、命中计算、窗口层级常量和默认位置，但全桌面拖动、Space 与锁屏恢复保留为明确人工闸门。无法自动化不能写成失败或通过，只有用户在冻结候选上给出明确结论后才能升级整链状态。

## 系统 Python 缺少 Pillow 导致正式包首轮编译未启动 · 2026-08-10

- 现象: 使用系统 `python3` 启动正式包编译立即报 `ModuleNotFoundError: No module named 'PIL'`，目标目录尚未产生。切换到仓库 `.venv/bin/python` 后，53 个 clip 和 6,925 条完整性记录正常编译。
- 根因: 非交互 shell 的 `python3` 解析到 Apple Command Line Tools Python，而项目 Pillow 12.2.0 安装在隔离 `.venv`。解释器版本可运行不代表项目依赖存在。
- 结论/避免: 所有素材编译和 QA 命令显式使用 `.venv/bin/python`，Swift 测试继续使用独立的 `tools/test-swift.sh`。失败后先确认没有部分产物，再从冻结配置重跑，不在系统 Python 中安装依赖。

## 沙箱内 hdiutil create 失败不代表附件内容损坏 · 2026-08-10

- 现象: 发布附件构建在沙箱中执行到 `hdiutil create` 时返回“设备未配置”。此前 App ZIP、素材包 ZIP 和 DMG 暂存目录已经部分生成，但没有完整发布元数据。
- 根因: `hdiutil` 需要真实 macOS 磁盘映像和设备能力，当前受限执行环境不能完成该系统操作。失败发生在容器权限边界，不是素材、App 或 DMG 布局本身的校验结论。
- 结论/避免: 把不完整输出整体保留为带 `failed-sandbox-hdiutil` 后缀的失败证据，不复用其中任何附件。获得真实 macOS 权限后从冻结 App 和素材包重新执行完整构建，并要求 ZIP 解包测试、`hdiutil verify`、字节数和 SHA-256 全部成功后才生成发布清单。

## 透明 PNG 事实源决定当前公开包体积 · 2026-08-10

- 现象: `v0.3.1` App 主程序约 1 MB，但内嵌宠物包约 465 MB，DMG 约 454 MiB。包中有 53 个 clip、6,866 个运行时帧和约 286 秒动画。对帧文件做精确 SHA-256 去重后没有可直接消除的重复帧，ZIP 与 DMG 也只能小幅压缩已经压缩的 PNG。
- 根因: 当前运行时把通过人工验收的逐帧透明 PNG 作为精确寻址事实源，并保留毛发边缘、Alpha、碰撞和动作图帧级契约。大部分体积来自媒体，不来自 Swift 二进制，也不是重复上传独立宠物包造成的 App 内部冗余。
- 结论/避免: `v0.3.1` 先取消 Release 中重复的独立宠物包附件，但不为缩小 DMG 修改获批帧。后续用代表性动作受控比较逐帧 WebP、带 Alpha 视频、图集和降采样 PNG，必须通过 Retina 视觉、透明边缘、逐帧寻址、预加载、内存和动作接缝验收后才能改变运行时编译格式。

## HEVC 文件小不等于桌面运行时 CPU 低 · 2026-08-10

- 现象: HEVC Alpha 明显减小磁盘与进程内存，但逐帧通过 AVAssetReader、CIImage、CGImage 和 NSImage 转换时 CPU 仍高。直接 AVPlayerLayer 后进程指标下降，但 VideoToolbox 系统解码进程仍占资源，单看 App PID 会低估总成本。
- 根因: 编码格式只决定存储与解码入口，真正长期成本还包括像素格式转换、图像对象创建、Alpha 合成和系统解码。把每帧重新包装成 AppKit 图像抵消了硬件视频解码的收益。
- 结论/避免: 性能比较同时记录 App PID、相关系统解码进程、physical footprint、采样工具和画面链。长期默认路径不做逐帧 `CIImage → CGImage → NSImage` 重建。视频路线只有在直接图层仍满足逐帧动作图与命中契约时才继续评估。

## Gatekeeper 延迟放行会制造两个宠物与错误性能归因 · 2026-08-10

- 现象: 新 QA bundle 通过 `open` 启动后先被 Gatekeeper 挂起或拒绝，稍后 AppTranslocation 又启动旧请求；同时直接运行当前二进制会出现两只宠物。另一次后台出现历史 `0.2.0-preview.10`，单独占用约 7.5% CPU 与 236 MiB，容易误判为当前候选回归。
- 根因: LaunchServices、AppTranslocation 与直接执行是独立启动路径，ad-hoc 新 bundle 的系统确认存在延迟。早期二进制没有跨版本单实例锁，进程名又都叫 `petsgraph`。
- 结论/避免: 性能测试前按完整命令路径和 PID 列出所有实例，精确终止旧版本，再采样唯一当前进程。main 分支 GUI 在包加载前获取每用户文件锁，重复启动立即退出；校验模式不竞争锁。测试中不要同时使用 `open -n` 与直接执行，也不要把 Gatekeeper 等待时的 0 CPU 假进程写成应用稳定态。

## 独立生成的软毛毯边无法共享不可逆褶皱状态 · 2026-08-13

- 根因: 软毛毯的褶皱、团起和压痕属于带历史的不可逆状态。多条独立生成视频只知道各自首尾图，没有共享前一条边形成的褶皱历史；静态分层也无法同时满足猫对毛毯的真实挤压。
- 结论/避免: 道具图先判断状态是否容易在独立边之间复现。飞流首版改用有稳定外轮廓和明确承重点的猫窝，并以同款猫窝静态谱系、统一几何锚点和最小坐睡链验证后再扩图。毛毯素材保留为失败证据和未来研究，不靠硬切、静态底图或逐帧修补伪造连续性。

## 静态端点视觉一致不等于道具几何一致 · 2026-08-13

- 现象: 五张人工通过的猫窝端点都像同一款猫窝，但机械测量发现猫窝像素宽度最多相差约 21%，其中一张整体前景还接近源画面右边界。若直接作为视频端点，容易在切换时出现道具缩放或裁切。
- 根因: 静态生成服务分别重绘了猫窝尺寸与镜头占比。人工验收关注身份、姿势和整体真实感，不会自动冻结跨图的像素坐标契约。
- 结论/避免: 视频生产前先做端点族审计。只在编译副本上按道具宽度、底部中心做每端点一次固定等比缩放和平移，再放入带安全边距的统一生成画布。不能按猫脸、身体或逐帧包围盒重新居中；静态对齐也不能升级为动作、抠图或运行时通过。

## 飞流旧拼接透明链放大了尺度、道具和抠图不一致 · 2026-08-15

- 根因: 旧流程把不同生成谱系、不同端点尺度和不同抠图策略的片段先后拼接，试图靠后期裁剪、局部补丁和分段抠图修补。这样会把局部通过误认为整链通过，也让同一猫窝和同一只猫在相邻片段中缺少共享历史。
- 结论/避免: 飞流旧完整拼接链、混合透明帧链和分段抠图成果不得进入正式候选。后续先验收未抠图源视频母片的尺度、道具谱系、端点和动作自然度；源片通过后再切片，最后对同一谱系的完整通过链统一抠图。提交给 Maxwell 前必须先自审大小跳变、出边框、道具漂移、背景污染和抠图一致性。

## 精抠重新拟合几何会破坏已经通过的粗抠接缝 · 2026-08-17

- 现象: 飞流各最小素材完成粗抠并通过逐闭环对齐后，早期精抠尝试再次出现体型忽大忽小、落地点高低变化和主体缺胳膊少腿。单段透明边缘看起来更干净，完整动作图却丢失了此前已经通过的相对位置关系。
- 根因: 精抠与空间对齐被错误耦合。新 alpha 包围盒被当作重新缩放和平移的依据，同一素材在不同闭环中可能获得不同几何；过强的统一清理又把长毛、脚掌和尾巴当成背景。
- 结论/避免: 先在保守粗抠上确定每个唯一 clip 的整段固定变换，并以逐闭环人工通过结果锁定。后续精抠只修改透明度与边缘颜色，不重新拟合几何。已经干净的素材逐字节复用，只选择性重做问题片段，并对耳朵、鬃毛、胡须、四肢、脚掌和尾巴设置主体保护检查。最终必须在深色、浅色、棋盘格和完整动作图中复核后再交付。

## 受限沙箱中的 hdiutil 失败不能归因于 App · 2026-08-18

- 根因: macOS 磁盘映像设备能力被沙箱拦截，不是 App 内容、签名、媒体或 DMG 布局错误。
- 结论/避免: 先确认发布目录不存在可误用的半成品，再以明确的磁盘映像权限重跑相同确定性构建。只有 `hdiutil verify`、挂载校验、字节数和 SHA-256 全部通过后，才写入发布清单和创建草稿 Release。

## WPF `Pbgra32` 不能直接解释包内 RGBA 字节 · 2026-08-18

- 现象: schema `0.4.0` 包内媒体按预乘 RGBA 存储，WPF `WriteableBitmap` 使用 `Pbgra32`。如果直接复制字节，红蓝通道会交换，但 alpha 和字节长度检查仍可能全部通过。
- 根因: 媒体契约和平台帧缓冲的通道顺序不同，“都是四通道预乘像素”不代表可以零拷贝互换。
- 结论/避免: 包内 RGBA 继续是跨平台事实，Windows 渲染器在写入 `Pbgra32` 时显式交换 R/B，保留 G/A。单元测试使用不对称的 R/G/B 样本字节，避免灰阶或红蓝相等素材掩盖问题。

## 透明命中正确不代表窗口视口契约正确 · 2026-08-18

- 现象: Windows 原型已经能按 alpha 让透明区鼠标穿透，但如果窗口仍直接使用完整制作画布，656×224 等宽画布会在桌面上形成大量透明窗口空间，也会让布局、拖动持久化和场景转换与 macOS 已批准体验不一致。
- 根因: 命中测试只决定鼠标事件给谁，不决定窗口的可见尺寸、制作画布原点或 clip 切换时的空间连续性。
- 结论/避免: 跨平台移植必须同时迁移 clip 级固定正方形视口、完整画布坐标映射、ground anchor、presentation offset、root motion 和当帧可见内容边界。窗口收紧只改变呈现区域，不改媒体字节或获批坐标。

## GitHub Windows Runner 通过不等于 Windows 11 GUI 通过 · 2026-08-18

- 现象: GitHub 托管 Windows Runner 可以成功还原 .NET 10 锁定依赖、运行单元测试、编译 WPF、发布 self-contained x64 ZIP，并验证 AMD64 PE 和压缩包结构。这些检查全部通过时，仍没有人看到透明宠物窗口的真实桌面行为。
- 根因: 托管 Runner 的交互桌面不是目标朋友的 Windows 11 环境，CI 也没有覆盖多 DPI、鼠标穿透、托盘 Shell、锁屏恢复、多显示器和长时动画观察。
- 结论/避免: 证据始终分为本机静态/交叉编译、GitHub Windows CI、真实媒体 ZIP 校验和 Windows 11 真机 GUI 四层。只有最后一层用户明确通过后，才能把透明、DPI、托盘、拖动和长时运行写成已验收。

## `contents: read` 工作流 token 看不到草稿 Release · 2026-08-18

- 现象: v0.6.0 标签、清单和草稿附件均已存在，本机回读附件为 `uploaded` 且字节数、SHA-256 正确。Windows Release 复验运行 `32125109434` 检出标签和解析清单成功，但在 `gh release view v0.6.0` 返回 `release not found`，因此没有进入 ZIP 下载和内容校验。
- 根因: GitHub 对只有 `contents: read` 的 `GITHUB_TOKEN` 隐藏草稿 Release。草稿对本机已登录维护者可见，不代表同仓库工作流的只读 token 也可见。
- 结论/避免: 需要读取草稿附件的工作流经发布所有者明确授权后使用 `contents: write`，同时把命令边界固定为 `gh release view` 与 `gh release download`，不包含创建、编辑、上传、删除或发布操作。工作流定义从默认分支运行，并在步骤内显式检出不可移动的目标标签。遇到 `release not found` 时先核对 token 权限和草稿状态，不重新上传已经远端校验正确的大附件。

## Seedance 纯色背景仍会形成渐变和色相漂移 · 2026-08-22

- 现象: 即使提示使用纯色绿幕或其他单色背景，Seedance 仍可能生成摄影棚式亮度渐变、压缩波动、接触阴影、地面线或轻微色相漂移。按单一 RGB 阈值逐帧抠图时，毛发边缘和背景残留会闪烁。
- 根因: 视频模型把背景理解为受光照影响的场景，而不是逐像素恒定的数字色块；视频压缩和生成噪声又让同一视觉背景形成颜色族。
- 结论/避免: 先用短片校准实际背景颜色，不因工具历史默认固守青色。正式抠图从整段边界采样背景色族，结合颜色距离、通道差、主体连通性和去色溢，并对完整 clip 使用统一参数。若移动阴影、纹理或背景主体无法稳定去除，拒绝母片而不是逐帧硬救。

## 后期降速会降低有效帧率并破坏生命感 · 2026-08-22

- 现象: 快速生成的呼吸、醒来或起卧动作在后期降速后，虽然总时长变长，但相邻有效姿态不足，出现卡帧、重复帧或低帧率感。
- 根因: 时间拉伸不能补回模型没有生成的中间真实姿态。复制帧、帧混合、光流或 RIFE 只能制造运动表象，不能保证毛发、承重和身份真实。
- 结论/避免: 提示词和视频生成阶段直接要求缓慢、从容、低幅度动作，记录原生 FPS、正式播放倍率和速度处理。正式素材保持 `1.0x`，不通过后期降速、抽帧、复制帧或自动补间达到目标节奏。

## 独立动作片段通过不等于拼接后有生命感 · 2026-08-22

- 现象: 单独观看睡眠、坐起或场景片段都可能自然，拼成完整链后仍出现呼吸相位重置、体型跳变、道具变化、位置闪动和身份漂移。
- 根因: 独立生成片段没有共享完整的时间、承重、光线和道具历史。运行时硬切、淡入淡出或后期定位只能遮挡接缝，不能恢复缺失的物理连续性。
- 结论/避免: 优先生成较长连续生活链，并只在稳定帧、完整呼吸周期、自然遮挡或完全离场处切分。每个合法连接必须有独立生成和正常速度人工通过的有向边；未抠图完整图先通过，再统一抠图和固定几何。连接可见时重新生成或重新切分，不把修补责任交给 Player。

## CommandLineTools 编译器与 SDK 小版本漂移会制造 Swift 假失败 · 2026-08-23

- 现象: `xcode-select` 指向 CommandLineTools 时，`swift test` 同时出现用户模块缓存不可写，以及 Swift 6.3.3 编译器无法加载由 Swift 6.3.2 构建的 macOS 26.5 SDK。代码未变化，测试却在 manifest 编译阶段失败。
