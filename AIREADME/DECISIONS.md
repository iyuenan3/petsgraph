# DECISIONS：petsgraph

> Append-only。新增决策追加 ADR，不重写既有编号。

## ADR-001 · 第一阶段只做 macOS 单宠水平活动带 · 2026-08-09

- Problem: 多宠、跨平台、跨显示器和二维漫游会同时放大素材、行为和窗口系统风险，无法优先证明真实宠物质量。
- Constraint: 首要目标是单只真实宠物的外观一致、动作自然和陪伴感；用户已确认第一阶段范围。
- Decision: 第一阶段只做 macOS 单宠，宠物在当前显示器底部固定 y 的水平活动带左右移动，不跨显示器。
- Alternatives（否决）: 直接复用 petsdesk 九宠边界；从第一天追求跨平台；允许全桌面二维自由移动。
- Tradeoff: 第一阶段覆盖面更窄，但能把素材与真实窗口同步作为唯一关键路径。

## ADR-002 · 正式动作采用直接视频连续帧并设置三次止损门 · 2026-08-09

- Problem: 骨骼、局部拼接和补帧能通过部分机械指标，却无法可靠提供真实承重、遮挡和身份连续性。
- Constraint: 用户拥有足够 Seedance 额度，愿意为了质量生成更多素材，但不希望批量生成后才发现方向错误。
- Decision: 正式动作来源使用直接生成视频的连续帧；一次处理一个动作生产单元或一条有向边；每项最多 3 次受控尝试，每次必须改变明确变量。
- Alternatives（否决）: 骨骼、Hatch Pet、肢体拼接、RIFE、光流或自动补间作为默认路线；无限随机重试；一次批量生成完整动作包。
- Tradeoff: 有向过渡和左右方向会增加生成次数与人工验收，但充足额度被用于质量而不是减少素材边界。

## ADR-003 · 姿态与方向组成节点，循环和有向过渡组成动作图 · 2026-08-09

- Problem: `stand`、`sit` 等平面动作名没有表达朝向和端点兼容性，独立视频随机切换会产生体型、承重和尾巴硬跳。
- Constraint: 运行时需要安全退出、预加载、逐帧切换和自然返回路径。
- Decision: 图节点至少表达 `posture + orientation + stability`；稳定或步态循环挂在节点上；跨姿态、起步、加速、减速、停步和转向使用独立有向边。运行时边保持独立，但一个生成母片可以切出多个连续片段。
- Alternatives（否决）: 平面 action ID；所有动作两两直连；反向播放复用过渡；只靠相位匹配和速度曲线掩盖缺少的动作。
- Tradeoff: 图和素材数量增加，但每条边的物理语义、验收和回退都可解释。

## ADR-004 · PNG 序列是制作事实源，图集是可重建运行时编译物 · 2026-08-09

- Problem: 动态 WebP 和普通视频适合预览，却难以可靠支持逐帧寻址、独立时长、安全退出、碰撞和 root motion。
- Constraint: 第一阶段需要快速验证，未来又需要控制内存和解码成本。
- Decision: RGBA PNG 序列与帧清单是制作事实源；首个运行时直接播放序列帧；通过性能原型后可以编译分页图集；动态 WebP、GIF 和 MP4 只用于预览或导出。
- Alternatives（否决）: 动态 WebP 作为唯一运行时格式；只存不透明 MP4；一开始就锁定单张超大图集。
- Tradeoff: 初版包体更大，但调试、验收和格式迁移可控。

## ADR-005 · 逐帧累计 root motion 驱动真实原生窗口 · 2026-08-09

- Problem: 固定速度移动窗口再按比例调动画 FPS，无法表达每一步的真实推进、起停和减速，也容易产生滑步。
- Constraint: 用户明确要求走路缓慢移动、跑步快速移动，左右动作对应同方向桌面位移。
- Decision: 从动作视频同一时间轴提取累计 `rootMotionPt`；动画和窗口共享单调时钟；运行时直接采样累计位置并更新原生窗口 x。跑步平均速度验收目标至少约为走路的 2 倍。
- Alternatives（否决）: CSS 内部平移；行为系统独立固定速度；帧间 delta 累加；窗口撞边后瞬间反向。
- Tradeoff: 素材契约和运行时实现更复杂，但掉帧、暂停和恢复不会累积漂移，脚步与桌面位移可以共同验收。

## ADR-006 · 正式左右动作独立生成并独立验收 · 2026-08-09

- Problem: 真实宠物左右花纹、耳朵、眼睛、尾巴和身体特征可能不对称，水平镜像会制造错误身份。
- Constraint: 用户愿意增加生成素材以获得更好效果，并确认左右独立策略。
- Decision: 正式包默认 `mirrorSafe=false`；走路、跑步及相关过渡分别生成左向和右向；工程原型可以临时镜像验证方向，但不得以此补齐正式包。
- Alternatives（否决）: 默认只生成一侧并镜像；用后处理局部改花纹。
- Tradeoff: 位移动作和部分姿态数量接近翻倍，但能保留真实左右身份。

## ADR-007 · 素材生成 Skill 与离线运行时只通过数据包连接 · 2026-08-09

- Problem: 如果运行时理解模型 API、提示词、生成任务或私密照片，产品会被 provider、网络、成本和隐私绑定。
- Constraint: 用户自行 clone 项目并配置 Seedance 等服务，项目不提供付费素材生成。
- Decision: Skill 负责照片、provider、生成、抠图、标注、QA、人工暂停点和包编译；运行时只验证、安装和播放数据包，不包含 provider SDK 或生成凭据。包内禁止可执行脚本和原始私密照片。
- Alternatives（否决）: app 内置生成购买；运行时按需联网生成；包内携带 provider 配置。
- Tradeoff: 生成体验与桌面体验是两个明确阶段，但运行时保持离线、稳定和可复现。

## ADR-008 · 动作、图边与真实运行时整链分层验收 · 2026-08-09

- Problem: 单动作 GIF 自然不代表它能接上前后动作，也不代表窗口位移、预加载和中断在真实桌面成立。
- Constraint: 人工视觉是最终闸门，机械检测只能辅助；未批准候选必须与正式素材隔离。
- Decision: 结构化记录 `mechanical-pass`、`human-action-approved`、`human-edge-approved` 和 `runtime-chain-approved`。必需路径只有达到整链批准后才能进入正式安装。
- Alternatives（否决）: 脚本通过自动升级正式；单动作通过即安装；只靠文档文字记录当前状态。
- Tradeoff: 验收步骤增加，但能防止已批准单项与失败过渡混装，也能保持状态可追溯。

## ADR-009 · 素材质量优先，但首个交付必须是可上桌闭环 · 2026-08-09

- Problem: 只强调素材优先可能再次导致先生成大量独立动作，最后才发现动作图、抠图和窗口同步无法成立。
- Constraint: 用户确认交互只需自主活动、抚摸、拖动、玩耍、进食、隐藏和退出，素材质量是第一要务。
- Decision: 先完成并验收右向 `站立→走路→跑步→走路→站立` 的真实窗口闭环，再扩左向、姿态和活动；交互保持最小充分集，不与素材主线竞争。
- Alternatives（否决）: 先做完整交互系统；先生成全部动作；只做离线 GIF 不上桌。
- Tradeoff: 第一阶段早期动作覆盖很窄，但最早验证的就是产品最难、最有价值的完整体验。

## ADR-010 · 用户通过的每个素材单元必须固化生产履历 · 2026-08-09

- Problem: 最终视频和聊天结论无法回答素材由什么输入、模型、提示词、连续帧、处理方法和衔接相位产生，也无法可靠迁移到其他猫狗。
- Constraint: 原始照片、provider 凭据和私有生成上下文不能进入公开仓库或运行时包；生成模型即使使用相同 seed，也不承诺逐像素重演。
- Decision: 每个进入 `human-action-approved` 或 `human-edge-approved` 的动作或图边必须保存独立 `approved-recipe.json`，每只宠物维护 `approved-assets.json`。履历记录生成、选帧、确定性处理、事实源、输出、图接口、人工批准、已知取舍和剩余闸门。它保存在私有制作工作区，不默认进入安装包。
- Alternatives（否决）: 只保存最终视频；只保存提示词；只依赖 provider 控制台、聊天记录或 shell 历史；把全部私密工作区打进宠物包。
- Tradeoff: 每次通过后增加一次结构化固化和校验，但能区分可确定性复现的后处理与只能方法复用的随机生成，并为素材生成 Skill 提供跨宠物训练样本。

## ADR-011 · 同一高风险素材单元允许两个受控候选并行生成 · 2026-08-09

- Problem: 串行等待每个 Seedance 候选会延长单动作验收周期，但同时制作多个动作或多只宠物会把尚未验证的端点、抠图和运行时问题成批复制。
- Constraint: 一次仍只解决一个动作生产单元或一条有向边；每项最多三次受控尝试；所有付费任务必须独立留痕且结果未知时不能自动重投。
- Decision: 对同一高风险动作单元允许并行提交最多两个候选。候选必须使用相同已批准端点和生成参数，各自只改变一个明确提示假设，并分别计入三次止损门。首只宠物的 root motion 真实窗口链通过前，不并行展开不同宠物的完整素材生产。
- Alternatives（否决）: 所有候选严格串行；一次批量生成多种动作；在五百运行时闭环前同时生产多只宠物。
- Tradeoff: 单条边的等待时间缩短，但一次可能消耗两次生成额度，并且仍需对每个候选分别处理、记录和人工比较。

## ADR-012 · 首个真实窗口证据原型采用 Swift/AppKit · 2026-08-09

- Problem: Phase 0 必须证明逐帧 PNG、动作相位、累计 root motion 和真实透明窗口能在同一时间轴上工作，跨进程或 Web 渲染路线会额外引入同步变量。
- Constraint: 当前只需 macOS 单宠水平活动带；素材包和运行时契约必须保持可迁移；一次原型不能提前锁死永久技术栈。
- Decision: 首个证据原型使用 Swift Package Manager、Swift 核心库和 AppKit 透明 `NSPanel`。帧选择与窗口 x 都直接采样 `ProcessInfo.systemUptime`，运行时不累加帧间 delta。Swift/AppKit 只锁定 Phase 0 实验，真实整链通过前不宣布正式技术栈定案。
- Alternatives（否决）: 首轮使用 Tauri/WebView 并通过 IPC 高频移动窗口；继续只看离线视频；沿用 petsdesk 的独立速度模拟和动画 FPS 比例调整。
- Tradeoff: 原生同步路径最短且易于验证，但当前只覆盖 macOS，完整 Xcode 环境和 AppKit 生命周期增加了本地构建要求，后续仍要用内存、功耗、窗口行为和维护成本决定是否延续。

## ADR-013 · 不同母片通过固定路径变换进入全包坐标 · 2026-08-09

- Problem: 右向移动素材的源地面是 `y=532`，已批准睡眠素材的源地面是 `y=440`。直接合并会让同一宠物在动作组件之间改变桌面地面高度。
- Constraint: 已批准源帧不可修改；规范化只能作用于编译副本；同一动作路径只能使用一个固定变换；睡眠链 root motion 必须为零。
- Decision: 全包锁定 640px 源画布、320px 运行时画布、源地面 `y=532` 和运行时地面 `y=266`。睡眠四段统一在编译副本上应用固定平移 `(0,+92)`，不缩放、不逐帧居中，所有锚点写入全包坐标。
- Alternatives（否决）: 为每个节点切换包级地面；按逐帧 alpha 包围盒重新贴地；修改已批准 PNG；把窗口 y 当作动作的一部分上下移动。
- Tradeoff: 固定变换保留动作内部连续性和可追溯性，但当前移动与睡眠仍缺少真实桥接素材，不能仅凭坐标一致宣布整包可达或可安装。

## ADR-014 · 动作图显式寻址并拒绝 hidden 必需文件 · 2026-08-09

- Problem: 点号临时构建目录在真实 macOS File Provider 路径产生 `UF_HIDDEN` 标记，目录枚举又可能漏掉合法片段，导致包内容与加载结果不一致。
- Constraint: 用户不能承担手动 `chflags` 修复；图引用与完整性清单必须共同决定必需文件；历史包和失败证据要保留。
- Decision: 加载器从节点 `loopClip` 与边 `clip` 推导片段集合并显式读取，校验所有必需控制文件、片段和帧都在 SHA-256 清单中，同时拒绝缺失、篡改、符号链接或 hidden 必需文件。编译器使用非点号临时目录，并在目录安装前后检查 `UF_HIDDEN` 为零。
- Alternatives（否决）: 继续使用 `.skipsHiddenFiles` 枚举；忽略 hidden 标记；安装后让用户手动清标记；原位修改历史包。
- Tradeoff: 老编译器产生的 hidden 历史包会被新加载器拒绝，但它们仍作为不可加载的追溯证据保留；新版本通过重新编译产生，不覆盖历史目录。

## ADR-015 · 正面坐姿是方向中立节点，起身边必须表达行走意图 · 2026-08-09

- Problem: 把坐姿强行标成左向或右向会复制几乎相同的稳定循环；只生成原地起身再硬接走路，又会让坐到站缺少准备行走的物理意图。
- Constraint: 用户确认坐姿可以面向屏幕，并要求坐姿到站立时前腿向前迈出，因为该过渡的真实目标是准备行走。窗口只能在宠物开始朝目标方向迈步后移动。
- Decision: 使用单一 `sit.front` 稳定节点。坐姿进入左右步态时分别生成有向边，边内连续完成转身、起身与前腿迈步；root motion 在第一步明确朝目标方向开始，进入步态循环前接上对应已批准速度。
- Alternatives（否决）: 为正面坐姿复制左右节点；先原地站稳再硬切走路；坐着时提前匀速平移窗口；用同一素材镜像补齐方向。
- Tradeoff: 坐姿循环只需一份，但左右起步边仍需分别生成和验收，且素材批准后还要单独验收窗口位移曲线。

## ADR-016 · 运行时预览必须绑定批准配方并服从动作图约束 · 2026-08-09

- Problem: 私有批准配方可能在路径不变时被意外修改，演示序列也可能通过截断过渡或从任意循环帧离开而呈现一条看似连贯、实际不符合正式动作图的评审链。
- Constraint: 源帧和批准记录必须保持可追溯；普通自主行为只能在安全退出帧离开循环；有向过渡不可被普通请求中断，且必须逐帧完整播放。
- Decision: 新编译配置固定批准配方 SHA-256，编译器在复制事实源前校验配方身份、批准状态、事实源路径、帧数、FPS 和序列摘要。加载器同时验证演示过渡从第 0 帧完整播放一次、相邻姿态兼容、循环只在批准安全帧离开。预览链不得拥有比正式动作图更宽松的切换语义。
- Alternatives（否决）: 只校验配方路径存在；只依赖包级完整性清单；允许演示序列自由截取片段；把不安全切换留给人工观看发现。
- Tradeoff: 历史配置可以暂时缺省配方哈希以保持可读，但不能据此升级批准状态；新预览配置更冗长，换来从批准事实源到桌面评审链的确定性证据链。

## ADR-017 · 首个产品收敛为李五百睡觉陪伴 MVP · 2026-08-10

- Problem: 走路、跑步、点击目的地和真实窗口移动已经证明部分工程可行性，但这些能力持续增加方向、边界、全局点击和异常恢复复杂度。用户长期观看后确认，最有陪伴感的体验是五百安静睡觉和自然更换睡姿。
- Constraint: 产品本身不承担效率或任务价值。首个版本必须值得长时间留在桌面上，不持续抢夺注意力；已批准移动素材和历史证据必须保留。
- Decision: 第一款产品改为「李五百睡觉陪伴 MVP」。启动默认睡眠，随机时间更换普通或枕头睡姿；点击宠物在当前场景睡眠与正面坐姿之间切换；支持全桌面拖动、置顶、隐藏和退出。点击桌面目的地移动、自主走跑、玩耍、进食和舔毛不进入首发默认行为。已完成走跑素材作为未来可选能力保留。
- Alternatives（否决）: 继续把完整走跑闭环作为首发闸门；只播放单一静态睡姿；删除既有移动素材并否认其工程价值。
- Tradeoff: 首发功能表面更窄，但素材、调度和长期稳定性可以集中服务陪伴感。后续活动能力必须由真实长期观察提出，而不是为了展示动作数量加入。

## ADR-018 · 枕头是核心场景，网关、睡姿与交互坐姿分离 · 2026-08-10

- Problem: 如果普通睡姿、靠枕端点、枕头睡姿和点击坐姿共用模糊节点，枕头会在切换时突然消失，随机调度也可能频繁让五百醒来回到同一靠枕姿势。新增 B2 又可能制造没有叙事价值的中转动作。
- Constraint: 枕头睡眠属于 MVP 核心；现有靠枕 B 已经是多条已生成路径的严格端点；道具尺度、位置和接触关系必须连续；当前 B 是否适合长期作为网关仍需真实桌面短链验证。
- Decision: 动作图新增 `scene`、`role` 和自主资格语义。普通与枕头场景分别使用 `sit.front.floor` 和 `sit.front.pillow`。现有 B 作为 `pillow.gateway.leaning.right` 的正式候选，只负责场景进出、路径汇合、预加载和点击唤醒，不参与随机睡姿。枕头内部随机换姿优先使用直接边。先验证现有 B 的短循环与接缝，只有失败时才生成 B2。
- Alternatives（否决）: 每次枕头换姿都回 B；从枕头睡姿硬切到无枕头坐姿；立即新增 B2 并在所有旧路径前后增加适配桥；把枕头拆成未经验证的独立物理对象。
- Tradeoff: 图中增加场景和节点职责字段，也需要枕头场景专用坐姿与回程素材；换来道具连续、清晰点击语义和更少重复醒来动作。

## ADR-019 · 核心素材取消固定三次上限，继续受控生成 · 2026-08-10

- Problem: 固定三次止损门适合阻止无差别抽卡，却已经与实际高质量素材生产冲突。半仰卧枕头路径经过多次明确改动才收敛，用户也明确授权为核心素材进行多次 Seedance 调用。
- Constraint: 素材质量优先，生成额度充足；每次调用仍必须可追溯，网络未知不能重复付费，重复相同失败时必须改变动作设计而不是只换 seed。
- Decision: 核心素材不设固定尝试次数上限。每个候选必须声明新的失败假设或明确改变动作分解、端点、画布、提示约束或模型策略，并完整记录任务和人工结论。同一失败反复出现时暂停生成，先重新设计生产单元。ADR-002 与 ADR-011 中的固定三次数字由本决策取代，其余单动作、受控变量、失败留存和不批量扩散约束继续有效。
- Alternatives（否决）: 坚持三次后放弃核心姿势；无限只换 seed；一次批量提交大量动作再统一筛选。
- Tradeoff: 单个核心动作的成本和时间可能上升，但不会因人为次数上限接受低质量素材。项目需要更严格的任务账本和变更假设记录。

## ADR-020 · 安静陪伴默认从物理屏幕左下角启动 · 2026-08-10

- Problem: 透明宠物窗口从屏幕中间出现会遮挡主要工作区，也不符合宠物自然待在桌面边缘的空间感。使用 macOS 可见工作区又会把 Dock 安全区算入底部边距，导致宠物看起来悬在屏幕底边上方。
- Constraint: 用户仍需能够把宠物拖到全桌面任意 x 和 y；自主睡眠行为不得偷偷改变用户放置的垂直位置；普通工程预览不能被安静模式的产品默认值破坏。
- Decision: `quiet-sleep-companion` 首次显示使用物理屏幕 `frame.minX` 与 `frame.minY`，让窗口 x 为 0，地面锚点贴合物理屏幕底边。安静模式窗口层级高于 Dock，用户拖动后的 x 和 y 在本次进程内成为新基准。普通工程预览继续使用独立启动布局。
- Alternatives（否决）: 屏幕中心；可见工作区左下角；无条件恢复上次拖动位置；所有模式共用同一启动点。
- Tradeoff: 首次启动位置稳定且不打扰，但当前版本不会跨重启记住用户最后位置，多显示器策略也仍未展开。

## ADR-021 · 获批 preview 以帧不变方式晋级正式本地包 · 2026-08-10

- Problem: 人工验收针对冻结的 preview.10。如果正式构建再次处理或替换帧，就会让批准结论和安装产物脱节；如果直接原位改名，又会破坏预览证据和版本履历。
- Constraint: 已批准源帧不可修改，历史预览必须保留，正式包需要独立 ID、稳定版本、整链批准状态、完整性清单和非 preview Bundle ID。
- Decision: 保留 preview.10 不变，从其冻结配置通过只覆盖 package 与 runtime review 的 `0.2.0` 配置重新编译。正式包与 preview.10 的全部帧哈希必须逐项一致，允许变化的文件只有 `package.json`、`reviews/index.json` 和由二者决定的 `integrity.json`。正式 App 使用 `com.maxwell.petsgraph.quiet-companion`，本机 ad-hoc 签名，并在批准注册表中记录完整证据哈希。
- Alternatives（否决）: 原位覆盖 preview.10；重新生成或重新抠图；把等待人工验收的状态直接当作正式状态；在没有 Developer ID 与公证时宣称公开发行。
- Tradeoff: 本地包可安装且批准链闭合，但它仍是私有工作区产物，公开分发还需要签名、公证和安装体验设计。

## ADR-022 · 指定睡姿复用动作图并只保留最后目标 · 2026-08-10

- Problem: 朋友希望从菜单直接看到和选择某一种睡姿。如果菜单直接播放目标循环，会绕过安全退出、预加载、道具进出和批准过渡；如果把每次选择全部排队，又会让五百长时间追赶过时指令。
- Constraint: 正式过渡不可中断；普通和枕头睡姿必须保持场景连续；用户界面不能显示内部节点或片段名称。
- Decision: 图节点增加可选 `displayName`，安静陪伴的自主睡姿强制提供非空中文名称。菜单从动作图派生 10 个目标。睡眠中立即规划，坐姿先自然返回睡眠，不可中断过渡期间只更新一个最后目标。所有路径继续使用安全退出、目标预加载和逐帧播放。
- Alternatives（否决）: 直接硬切到目标循环；为菜单维护独立视频播放表；保存无界命令队列；在用户界面显示 clip ID。
- Tradeoff: 用户的后一次选择会覆盖尚未执行的前一次选择，但视觉连续性和响应可预测性得到保护。

## ADR-023 · 正式媒体使用 GitHub Release 附件而不是 Git 历史 · 2026-08-10

- Problem: 五百正式 App、DMG 和素材包各约 460 MB。朋友需要公开下载完整素材，但把这些二进制写入 Git 对象会永久膨胀 clone、历史和维护成本。
- Constraint: 正式附件必须版本化、可核验、可回滚；原始照片、生成任务和失败候选继续私有；代码与五百媒体的授权边界不同。
- Decision: Git 只保存代码、文档、构建工具和包含文件名、字节数、SHA-256 的小型清单。DMG、App ZIP、素材包 ZIP、睡姿总览和校验和作为版本化 GitHub Release 附件公开。代码遵守 MIT，五百媒体遵守 `ASSETS.md`。
- Alternatives（否决）: 把运行时帧直接提交到 Git；使用 Git LFS 作为首版强依赖；只公开代码不让朋友看到五百；公开整个私有生产工作区。
- Tradeoff: 本地和 CI 发布步骤需要上传并再次下载较大的附件，但普通 clone 保持轻量，公开内容边界也更清晰。

## ADR-024 · 首个公开版仅支持 Apple 芯片并由验证工作流发布 · 2026-08-10

- Problem: 首批用户只需要 Apple 芯片 Mac。扩大到 Intel 会增加构建矩阵、包体和未验证环境；本机又没有 Developer ID 身份，无法完成 Apple 公证。
- Constraint: 不得把 ad-hoc 签名描述为无提示安装；草稿附件只有和精确标签、清单与测试一致时才能成为正式最新版。
- Decision: `v0.3.0` 只构建 `arm64`，最低 macOS 14。先创建带全部附件的草稿 Release，再由 GitHub Actions 检出精确标签，运行完整 XCTest，核对全部字节数、SHA-256 和 App 架构，全部通过后发布草稿。安装文档明确首次右键打开或在隐私与安全性中确认。
- Alternatives（否决）: 首版同时构建 Intel 和通用二进制；跳过远端附件核验直接发布；在没有证书时宣称已签名公证；等待公证完成后才让朋友试用。
- Tradeoff: Intel 用户暂时不能安装，首次打开存在系统确认步骤；换来更小的验证范围和可审计的公开发布链。

## ADR-025 · 通用 App 品牌与宠物包身份分离 · 2026-08-10

- Problem: `0.3.0` 的 App、Bundle ID 和附件名称都绑定李五百睡眠场景。未来加入其他宠物时，继续沿用这套命名会让用户把运行时、宠物身份和行为模式误认为同一产品，也会重复上传已经内嵌在 App 中的素材包。
- Constraint: 当前公开内容仍然是李五百安静陪伴，已批准素材帧不得因品牌调整而变化；历史 `v0.3.0` 标签和附件必须保留；首批朋友应只需下载一个安装入口。
- Decision: 从 `v0.3.1` 起，App、菜单栏可访问名称和 DMG 统一使用 `PetsGraph`，Bundle ID 使用 `com.maxwell.petsgraph`。当前宠物名称从内嵌包的 `pet.displayName` 读取，菜单显示「当前宠物：李五百」，运行时反馈不得写死具体宠物名。Release 只发布 DMG、备用 App ZIP、当前宠物睡姿总览和校验和，不重复发布独立 `.petsgraph-pet`。
- Alternatives（否决）: App 继续叫「李五百睡觉陪伴」；每只宠物发布一个独立命名的运行时；把宠物名硬编码在通用 UI；同时发布 App 和内容完全重复的宠物包附件。
- Tradeoff: `v0.3.1` 的安装身份与 `v0.3.0` 不同，用户可能在应用程序中短期看到两个 App。换来长期稳定的通用运行时品牌、可替换宠物身份和更清楚的发布附件边界。

## ADR-026 · 低功耗候选采用固定 clip 裁剪的预乘 RGBA · 2026-08-10

- Problem: 正式 v0.3.1 的逐帧 PNG 路线保持视觉质量和精确寻址，但真实桌面稳定态约占 4.4% 到 5.9% CPU 与约 215 MiB 内存，不适合长期陪伴。HEVC Alpha 能减小磁盘与进程内存，但每帧经 `CIImage → CGImage → NSImage` 重建会提高 CPU；直接视频图层仍要统计 VideoToolbox 系统解码成本。
- Constraint: 获批 PNG 与帧序不得修改；同一动作只能使用固定空间变换；安全退出、碰撞、点击、root motion 和预加载必须继续逐帧寻址；用户明确接受用磁盘换 CPU 与内存。
- Decision: PNG 继续作为不可变制作事实源。schema `0.4.0` 为每个 clip 计算一次全帧 alpha 并集并增加固定 4 px 透明边距，将所有帧按同一 crop 编译为 sRGB `rgba8-premultiplied` 连续流。运行时只读内存映射媒体，Core Graphics provider 直接引用映射字节，CALayer 在包级完整画布坐标中放置 crop。小循环整段预建，长过渡按固定 crop 有界分块。GUI 增加每用户单实例锁。
- Alternatives（否决）: 继续全画布 PNG 全量解码；把 HEVC 每帧转成 AppKit 图像；逐帧重算 crop 或重新居中；只用动态 WebP；为了省磁盘删除批准 PNG；在未人工视觉通过时直接替换 v0.3.1。
- Tradeoff: 完整候选从约 465 MB PNG 增长到约 1.827 GB raw 媒体，但普通睡眠降到约 1.3% 到 1.6% CPU 与 53 MiB，连续过渡约 2.1% 到 2.7% CPU 与 19 到 46 MiB。启动完整性哈希仍需读取大文件，Release 体积可能增加。候选保持 `installable=false`，完整视觉、点击拖动、锁屏恢复和长时间运行验收通过后才决定下一版本默认格式。

## ADR-027 · v0.4.0 正式采用固定裁剪 RGBA 并保留 PNG 回滚基线 · 2026-08-10

- Problem: v0.3.1 PNG 运行时已经通过完整桌面验收，但长期稳定态约占 4.4% 到 5.9% CPU 与约 215 MiB 内存。低功耗候选达到资源目标后，需要决定是否作为朋友安装的正式默认包，同时避免丢失人工批准事实源和可回滚版本。
- Constraint: v0.4.0 不得重新生成、抠图、补帧、逐帧定位或修改批准源帧；正式包必须可追溯到已批准来源；远端发布不得接受错版本、候选状态或未校验媒体；用户明确接受用磁盘换长期 CPU 和内存，并授权发布 v0.4.0。
- Decision: v0.4.0 使用 schema `0.4.0` 与 `cropped-rgba-clips` 作为正式默认运行时，包状态为 `runtime-chain-approved` 与 `installable=true`。编译器只有在来源包已批准且显式传入 `--release-approved` 时才允许晋级。App、素材包和 Release 版本必须一致；GitHub Actions 核对 schema、渲染模式、批准状态、剩余闸门、附件哈希、arm64 架构和完整测试后才发布。v0.3.1 PNG Release 与私有 PNG 包永久保留为回滚基线。
- Alternatives（否决）: 继续公开高资源 PNG 默认包；删除 PNG 只留 raw；把 HEVC Alpha 对照直接升级正式；让 GitHub Actions 重新编译另一份未在本机验收的 DMG；仅凭文件名把候选包标记为可安装。
- Tradeoff: 解压后 App 从约 465 MB 增长到约 1.827 GB，DMG 从约 454 MiB 增长到约 548 MiB；换来普通睡眠约 1.3% 到 1.6% CPU 与约 53 MiB physical footprint、连续换姿约 2.1% 到 2.7% CPU 与约 19 到 46 MiB，以及重复启动保护。发布链上传和下载时间增加，但 Git 历史仍保持轻量。

## ADR-028 · 素材生产改为少量真实宠物的人工定制 · 2026-08-12

- Problem: 李五百与飞流的真实睡姿、体型、道具偏好、受力关系和可接受动作图差异很大。把一只宠物的十姿势模板推广为任意宠物的自动流程，会把最重要的身份和自然度变成最低公分母。
- Constraint: 项目价值来自熟悉宠物的高质量陪伴；Maxwell 只需要为自己的猫狗和少量朋友委托制作，不需要素材市场、自助上传或规模化付费服务；离线运行时和数据完整性仍值得复用。
- Decision: 取消面向所有用户的一键通用素材生成 Skill 目标。保留 provider 适配、任务账本、抠图、坐标、QA、批准履历和包编译等内部工具，每只宠物单独研究真实习惯并设计姿态、道具、动作图和行为权重。朋友需求采用明确委托与逐项人工验收。
- Alternatives（否决）: 固定十姿势模板套用所有宠物；让用户上传照片后自动发布；因为素材不通用而为每只宠物复制一套运行时代码。
- Tradeoff: 单只宠物生产仍然耗时，无法承诺自助规模化；换来更高身份一致性，也保留共享 App、播放器、完整性和低功耗渲染的工程复用。

## ADR-029 · 飞流使用加权随机动作图与毛毯场景坐姿枢纽 · 2026-08-12

- Status: 已由 ADR-031 和 ADR-033 废弃。毛毯分支、毛毯坐姿和对应流程只保留为历史制作证据。

- Problem: 串行闭环适合检查接缝，却会让正式宠物像固定轮播。若从十个循环中直接随机抽取则会硬切。飞流在毛毯睡觉时点击醒来，如果复用无道具坐姿，毛毯会瞬间消失；若每次换毛毯睡姿都坐起，又会破坏睡眠感。
- Constraint: 所有变化必须沿人工通过的有向边；随机睡姿不应近期重复或频繁跨场景；飞流喜欢踩奶，但它是偶发活动；毛毯的位置、尺度、形状、明暗和接触关系必须连续。
- Decision: 正式行为在宠物动作图上做加权随机游走，使用随机长尾停留、近期两个姿势冷却、节点权重、场景粘性和活动冷却。地面平趴睡与毛毯蜷睡分别作为睡姿子图枢纽。新增 `sit.front.blanket`，飞流直接坐在同一张毛毯上；它承担毛毯点击坐姿、场景进出和路径汇合，设置 `role=interaction`、`autonomousEligible=false`。它可以在场景进出路径中短暂停留，用户点击醒来后则停在这里；毛毯内部普通随机换姿不经过该坐姿。踩奶从毛毯蜷睡出发并返回，由独立活动冷却触发。
- Alternatives（否决）: 固定串行播放；循环视频等概率硬切；所有毛毯换姿先坐起；点击毛毯睡姿后硬切到无道具坐姿；为全部睡姿两两生成直接边。
- Tradeoff: 新增毛毯坐姿循环和必要双向边，运行时还要扩展 `blanket` 场景与行为参数验证；换来低重复、场景连续且可解释的随机陪伴。

## ADR-030 · gpt-image-2 进入静态制作侧但不进入动作与运行时批准链 · 2026-08-12

- Problem: Seedream 在部分静态身份和姿态基准上有效，但安全画布、端点编辑和多方案比较需要第二条静态生成路线。把静态图片结果直接当作动作素材，又无法证明时间连续、承重和接缝自然。
- Constraint: 新配置只存在于被 Git 忽略的 `.env.local`；凭据不得进入仓库、文档、日志或宠物包；Seedance 仍是正式连续动作视频来源；人工验收保持最终闸门。
- Decision: 制作侧支持通过 `GPT_IMAGE_API_KEY`、`GPT_IMAGE_MODEL`、`GPT_IMAGE_GENERATIONS_URL` 与 `GPT_IMAGE_EDITS_URL` 调用 `gpt-image-2`。用途限定为身份基准、静态姿态设计、安全画布、outpaint 和 Seedance 严格端点参考。记录请求方法、模型标识、输入输出哈希和人工结论，不记录密钥值或完整认证头。静态图批准不能自动升级为动作批准、整链批准或可安装。
- Alternatives（否决）: 只允许一个静态 provider；把 gpt-image-2 放进桌面 App；用静态补画或帧间生成代替 Seedance 连续视频；在 AIREADME 中记录真实 key 方便复现。
- Tradeoff: 制作工具需要维护另一个响应契约和安全日志边界，但可以更快建立高质量端点，同时不改变离线运行时与动作验收标准。

## ADR-031 · 飞流首版以猫窝场景替代毛毯场景 · 2026-08-13

- Status: 猫窝替代毛毯的方向继续有效；其中 6 个无道具睡姿、猫窝坐姿场景进出网关和 10 睡姿首版目标已由 ADR-033 废弃。

- Problem: 毛毯在坐起、躺下和换姿时会发生真实褶皱与堆叠，生成视频却难以在多条独立边中恢复为同一形状，已经反复出现毛毯突变、闪动和接缝不一致。继续把静态毛毯锚点逐条接成图，会把不可逆软体状态分散到多条互不共享历史的视频。
- Constraint: 飞流首版仍需要 10 个高质量睡姿和有道具核心场景；用户接受在场景切换视频中移动；猫窝必须足够大并保持同一款式、尺度、镜头、明暗与承重关系；所有已批准源图不可修改；每条路径只能在编译副本上使用一次固定空间变换。
- Decision: 飞流首版冻结为 6 个无道具睡姿与 4 个猫窝睡姿。`sit.front.cat-bed` 是点击和场景进出的交互网关，`rest.cat-bed.curled` 是猫窝内部自主睡姿枢纽，分别连接自然趴睡、侧伸睡和舒展露腹睡。五张已通过静态端点按猫窝宽度与底部中心确定性对齐到统一安全画布，静态通过只允许进入视频生产。历史毛毯与踩奶资产完整保留但不进入首版动作图；踩奶如需恢复，必须针对猫窝重新设计。
- Alternatives（否决）: 把毛毯作为静态底图并让猫层独立运动；要求每条独立视频自动恢复同一褶皱；继续增加毛毯 inpaint 修补；删掉所有道具睡眠；让每个猫窝睡姿都先回到坐姿。
- Tradeoff: 已完成的毛毯循环和踩奶暂时不能进入首版，猫窝仍会产生局部压缩差异并需要逐边验收；换来更稳定的道具轮廓、清晰的承重点和可扩展的随机动作图。

## ADR-032 · 原帧倒序只作为同节点偶发自环的人工批准例外 · 2026-08-13

- Problem: 普通姿态转换倒放会让重心转移、道具压缩和关节发力失真，因此项目一直要求独立回程；但飞流舒展露腹睡的伸懒腰在正向动作后原帧倒序返回，经完整视觉验收比多次重新生成的回程更自然，而且始终返回同一姿态节点。
- Constraint: 不能放宽不同姿态节点或不同场景之间的有向边规则；批准源帧不得修改；不能使用插帧、光流、RIFE、交叉淡化或自动补间掩盖接缝；偶发动作必须完整播放且目标基础循环预加载完成。
- Decision: 允许同一节点上的低频偶发表现自环在人工明确验收完整正放加倒放预览后，按配方使用批准源帧正序一次，再追加去重峰值帧后的精确倒序。配方必须记录正放与倒序帧范围、不可中断、root motion 为零和回到同节点基础循环。所有不同节点或场景之间的回程继续独立生成、独立验收，`↔` 永远不表示倒放。
- Alternatives（否决）: 禁止所有倒序导致已经视觉通过的自然自环无法使用；把倒序普遍用于起身、躺下或场景转换；通过插值或淡化修饰不自然回程。
- Tradeoff: 编译器与校验器需要识别一个显式、可审计的 self-edge 组装模式；换来更自然且确定性的偶发表现，同时不破坏普通动作图的物理方向性。

## ADR-033 · 飞流首版动作图简化为双枢纽睡眠图 · 2026-08-15

- Problem: 旧飞流动作流程包含收爪趴睡、半仰睡和猫窝正面坐姿场景进出网关，导致必需过渡数量增加，也把已经不稳定的猫窝坐姿卷入跨场景移动。素材反复拼接后出现尺度跳变、猫窝变化、出边框和抠图不一致，说明继续补旧流程会扩大失败面。
- Constraint: 用户已经确认新的动作流程；飞流首版仍保留无道具和猫窝两个核心场景；点击当前场景的宠物必须能到达该场景坐姿；正式随机仍沿动作图，不硬切，不倒放跨节点边。
- Decision: 废弃此前飞流动作流程稿。首版使用 8 个自主睡姿和 2 个交互坐姿：`sit.front.floor ↔ rest.floor.prone.right`；平趴睡分别双向连接侧身伸展睡、紧蜷睡、仰躺睡和 `rest.cat-bed.curled`；猫窝蜷睡分别双向连接 `sit.front.cat-bed`、猫窝自然趴睡、猫窝侧伸睡和猫窝舒展露腹睡。`rest.floor.loaf.front` 与 `rest.floor.semi-supine.right` 不进入飞流首版动作图。`sit.front.cat-bed` 只服务猫窝点击坐姿，不作为地面与猫窝场景切换网关。
- Alternatives（否决）: 继续追求十个飞流睡姿；保留收爪趴睡作为点击入口；让半仰睡作为仰躺睡前置；所有猫窝进出都经过猫窝坐姿；用已失败的拼接透明链继续修补。
- Tradeoff: 首版睡姿数量减少，但图结构更短、待生成边更少、点击语义更清晰，也降低猫窝谱系和抠图不一致的风险。

## ADR-034 · 飞流当前图恢复半仰路线并冻结精抠整段几何 · 2026-08-17

- Problem: ADR-033 为降低失败面排除了半仰睡，并让平趴睡直接连接仰躺睡。后续素材制作已经完成并人工通过平趴睡往返半仰睡、半仰睡往返仰躺睡，以及全部猫窝分支。粗抠闭环通过后，若精抠再次根据 alpha 包围盒拟合位置，会重新制造体型和落地点跳变。
- Constraint: 当前人工通过的素材关系必须完整保留；收爪趴睡和睡眠香箱暂不进入图；每个 clip 只能使用一个已经通过的整段固定缩放与平移；精抠不能牺牲飞流的耳朵、鬃毛、胡须、四肢、脚掌和尾巴，也不能修改帧序或批准速度。
- Decision: 当前飞流图冻结为 9 个自主睡姿和 2 个交互坐姿，共 11 个节点、20 条有向边和 31 个唯一素材。地面平趴睡连接正面坐姿、侧身伸展睡、紧蜷睡、半仰睡和猫窝蜷睡；仰躺睡只经半仰睡往返。猫窝蜷睡连接猫窝正面坐姿、自然趴睡、侧伸睡和舒展露腹睡。精抠沿用粗抠整链已经通过的固定几何，只选择性更新 12 条有问题的地面素材，另外 19 条干净素材逐字节复用。完整精抠图由 Maxwell 人工通过，但不自动获得运行时或安装批准。
- Alternatives（否决）: 继续排除已经通过的半仰睡；恢复收爪趴睡或睡眠香箱；让平趴睡直接连接仰躺睡；精抠后重新拟合每帧或每闭环的大小和位置；为了统一算法重做全部 31 条素材。
- Tradeoff: 从仰躺睡到地面坐姿需要依次经过半仰睡和平趴睡，路径更长；换来已通过素材的完整保留、可解释的承重变化、稳定的全图相对位置和更低的精抠回归风险。

## ADR-035 · 一个 App 装载多只独立宠物并提供全局显示倍率 · 2026-08-18

- Problem: 五百已经公开使用，飞流素材图也已完成。如果为每只宠物发布独立 App，用户会得到多个菜单栏图标、重复进程、重复调度器和难以统一的安装体验；如果把多只宠物合进同一个动作图，又会破坏每只宠物独立的姿势、场景和随机节奏。
- Constraint: 首次安装默认同时看到五百和飞流；两只宠物各自随机变化，不锁步；菜单可以分别装载和指定睡姿；飞流视觉体型略大于五百；用户可以统一调整大小并持久化；当前不做宠物互动、碰撞和自动避让。
- Decision: 保持一包一宠，由单个 `PetsGraph` 进程组合多个包。每只已装载宠物拥有独立 `PetWindowController`、`BasicBehaviorSession`、随机状态、位置和菜单，App 只共享一个 24 Hz 渲染 scheduler。首次安装装载全部内嵌宠物，并在物理屏幕左下角按五百、飞流顺序横排。装载集合、每只宠物位置和全局七档倍率分别持久化。全局倍率按各包 `baseHeightPt` 同比缩放，保持当前 ground anchor、当前动作和包级相对体型。scene 目录改为宠物包数据，加载器不再写死场景白名单。
- Alternatives（否决）: 每只宠物一个独立 App；把多只宠物合进一个大素材包和共享动作图；让两只宠物共享随机计时；提供每只宠物独立倍率；为了避免重叠引入碰撞和自动布局引擎；把 `floor`、`pillow`、`cat-bed` 写死在菜单代码中。
- Tradeoff: 一个进程需要同时管理多个透明窗口和更大的内嵌媒体，双宠稳定态与同时过渡的 CPU、内存和启动成本必须重新验收。离散全局倍率不如滑块连续，但菜单状态可复现，也避免每一小步都触发窗口重排。用户拖动后允许重叠，减少当前版本的行为复杂度。

## ADR-036 · 桌面窗口使用 clip 级固定正方形视口 · 2026-08-18

- Problem: 飞流的统一制作坐标为 656×224，普通睡姿只占中间约三分之一。直接把制作画布映射为透明窗口，会让提示框异常宽、首次横排出现大段透明间隔，也让飞流的可见体型被安全留白掩盖。
- Constraint: 已批准素材帧、帧序、包内固定几何和接缝不得修改；地面往返猫窝的两条跨场景边确实使用更宽的动作区域，不能简单裁成一个全包小方框；同一 clip 内禁止逐帧追踪、缩放或移动素材。
- Decision: 每条 clip 从固定 RGBA alpha 并集裁剪或整段 `contentBoundsPx` 并集生成一个固定正方形视口。窗口边长取整段最大宽高，切换 clip 时通过统一制作坐标反算窗口原点，使相同素材坐标继续落在相同桌面位置。普通循环得到紧凑方形窗口，宽动作临时得到更大的方形窗口。提示框按文字宽度和当前可见主体定位。飞流候选包仅把 `baseHeightPt` 从 150 调整为 172.5，以建立略大于五百的桌面体型，素材媒体逐字节不变。
- Alternatives（否决）: 把 656×224 直接补成 656×656；把全包硬裁成 224×224；逐帧跟随主体移动视口；重新缩放或生成已经通过的素材；继续让提示框和启动布局使用整张制作画布边界。
- Tradeoff: 跨场景宽动作播放时透明方窗会暂时变大，但它仍然不可见，并完整保留动作。运行时需要在 clip 边界重算窗口尺寸、命中坐标和拖动持久化，因此必须通过真实桌面接缝、点击、拖动和资源回归后才能发布。

## ADR-037 · 屏幕边界只约束当帧可见内容 · 2026-08-18

- Problem: 跨场景过渡需要较大的固定正方形视口。当运行时使用透明视口外框判断屏幕边界时，方窗中不可见的留白会触发整个制作画布平移，在 clip 切换处制造额外横向跳动。宽方窗中心也不等于宠物中心。
- Constraint: 每条 clip 必须继续使用一个固定正方形视口，禁止逐帧裁剪、缩放或跟踪主体；可见宠物和道具不能离开屏幕；拖动与持久化仍使用统一制作画布原点。
- Decision: clip 视口仍决定 `NSPanel` 的尺寸和绘制映射，但水平屏幕边界判断改用当帧 `contentBoundsPx`。只有当帧真实可见内容即将越界时才能调整制作画布原点。行为会话的宠物水平中心改用当帧 ground anchor 的桌面坐标。
- Alternatives（否决）: 继续约束透明方窗外框；缩小宽过渡视口并裁掉动作；逐帧跟踪飞流；在每次 clip 切换时对宠物位置做经验偏移。
- Tradeoff: 透明方窗本身可以部分位于屏幕外，但可见内容仍被严格保留在屏幕内。这只能消除运行时额外制造的位移，不能修复源视频内已经生成的反向滑动；源动作错误仍必须重新生成并单独验收。

## ADR-038 · v0.5.10 使用短宠物名与单 DMG 发布 · 2026-08-18

- Problem: 旧版公开附件包含 DMG、ZIP、总览图和校验和，普通朋友实际只需要 DMG。菜单使用带姓氏的宠物名也与日常称呼不一致，并让通用 App 看起来绑定某一只宠物。
- Constraint: 历史标签和 Release 不能改写；正式媒体已经内嵌 App，不能重复进入 Git 或作为独立宠物包上传；远端仍必须核验字节数、SHA-256、架构、签名和内嵌包状态。
- Decision: v0.5.10 用户界面从包读取不带姓氏的熟悉短名，当前为“五百”和“飞流”，内部稳定 ID 不变。新 Release 精确只发布一个 `PetsGraph-v0.5.10-macOS-arm64.dmg`。仓库清单记录字节数和 SHA-256，GitHub Actions 下载、挂载并验证该 DMG 后发布草稿。不发布 App ZIP、预览图、校验和附件或独立 `.petsgraph-pet`。
- Alternatives（否决）: 继续使用“李五百”等全名；为每只宠物发布独立 App；继续维护四附件集合；把数 GB 媒体写进 Git；让 GitHub Actions 重新编译另一份未经桌面验收的 App。
- Tradeoff: 用户只有一个清晰安装入口，Release 更易转发；如果 DMG 下载失败则没有 ZIP 备用，但历史版本仍保留，附件完整性可由仓库清单和 GitHub 摘要验证。

## ADR-039 · 飞流正式显示基准比五百大 5% · 2026-08-18

- Problem: 飞流初始运行时基准与五百接近，视觉上显得偏小；后续放大 10% 后又显得过大，需要在不修改已批准媒体的情况下固定最终相对体型。
- Constraint: 不重新生成、不重新抠图、不缩放单帧，不改变动作接缝和统一制作坐标；全局七档倍率必须继续同比作用于所有宠物。
- Decision: v0.5.10 固定五百 `baseHeightPt=172.5`、飞流 `baseHeightPt=181.125`，即同倍率下飞流比五百大 5%。只修改飞流包级显示元数据并重新计算完整性，31 个运行时媒体文件保持不变。
- Alternatives（否决）: 保留 10% 差异；把两只宠物设为同高；在 Swift 代码里写死飞流缩放；逐 clip 或逐帧修改素材大小。
- Tradeoff: 相对体型成为当前两包的人工视觉校准结果，不代表真实厘米比例。未来新增宠物仍需单独校准自己的 `baseHeightPt`。

## ADR-040 · Windows 11 x64 采用 .NET 10 WPF 与无签名便携 ZIP · 2026-08-18

- Problem: 朋友需要在 Windows 电脑上使用 PetsGraph。新平台必须复用五百和飞流已批准宠物包，不能为迁就窗口系统重新生成、抠图或修改媒体，也不能把跨平台编译绿色写成真实 GUI 通过。
- Constraint: 目标设备固定为 Windows 11 x64；用户接受内部无签名分发与 SmartScreen 提示；不需要 MSIX 或安装器；应用必须离线、自包含运行时、保持一包一宠和原有动作图契约；宠物与当前内嵌道具必须正确命中与穿透。
- Decision: 新增 .NET 10 解决方案，核心层负责 schema `0.4.0`、安全加载、完整性、时间线、安静行为、累计 root motion 和 clip 级固定方形视口，WPF 层负责 RGBA 到 `Pbgra32` 通道转换、透明置顶窗口、Win32 透明命中、DPI 拖动、托盘、全局七档缩放、位置持久化和每用户 Mutex。产物固定为 `win-x64` self-contained 多文件 ZIP，默认不签名、不构建 MSIX。GitHub Windows Runner 只构建和校验不含私有媒体的代码运行包，真实双宠 ZIP 在本机从批准包确定性构建。
- Alternatives（否决）: Electron 或 WebView 重写；继续把 Windows 排除在需求之外；为 Windows 重新编译一套宠物媒体契约；把完整私有媒体放入 Git 或常规 CI artifact；首版同时做 Windows on Arm、Win10、MSIX 和签名；仅因 Windows Runner 通过就对外发布。
- Tradeoff: 双平台共享数据契约但保留原生窗口实现，代码和测试矩阵增加。便携 ZIP 简化内部分发，但用户需保留完整解压目录并理解未签名安全提示。Windows Server 2025 CI 可以证明编译、测试和产物结构，但真实 Windows 11 透明、DPI、拖动、托盘、多显示器与长时运行仍是必须人工完成的闸门。

## ADR-041 · v0.6.0 发布冻结的单一 Windows ZIP · 2026-08-18

- Problem: Windows 便携包接近 900 MiB，既不能写入 Git，也不应让 GitHub Runner 重新编译一份与朋友真机验收对象不同的附件。旧候选 App 和 ZIP 长期留在 `dist/` 还占用约 34 GB，并容易被误传为正式版。
- Constraint: 只支持 Windows 11 x64，内部朋友接受无签名和 SmartScreen 提示；朋友已经对冻结候选给出“没有问题”的最终验收结论，发布所有者明确授权 v0.6.0；本次没有分项时长或 DPI 日志，不能补写量化结果；历史标签、Release、批准素材和仓库履历不得删除。
- Decision: v0.6.0 精确发布一份本机冻结的 `PetsGraph-v0.6.0-Windows-x64.zip`，字节数为 `913953281`，SHA-256 为 `90578d6620ef9c221c173b173c24631d6e756b372b532030f8669994d22b0015`。仓库固定清单记录该附件，Windows Runner 从草稿 Release 下载同一文件并复验标签、附件集合、摘要、版本、AMD64 PE、双包数量和运行时完整性，成功后才允许发布。`dist/` 删除旧 macOS 候选 App 和 4 份废弃 Windows ZIP，只保留冻结正式 ZIP；历史正式产物继续由 Git 标签、GitHub Release、清单和批准包保留。
- Alternatives（否决）: 把媒体 ZIP 提交进 Git；让 CI 重新编译并发布另一份未真机验收的附件；保留所有候选并靠文件名人工辨认；使用 `--clobber` 原位覆盖已上传附件；为本次内部朋友分发增加 MSIX、签名或其他架构。
- Tradeoff: 发布附件与真机验收对象保持逐字节一致，下载入口和回滚身份清楚，也释放大量本地磁盘空间。代价是上传和远端复验耗时较长，Windows 真机结论目前只有最终反馈，没有可复查的分项量化日志。

## ADR-042 · v0.6.0 补充 macOS DMG 并分离 App 与宠物内容版本 · 2026-08-18

- Problem: v0.6.0 首次冻结时只发布 Windows ZIP，但同版本已经加入用户验收的双猫相伴 Logo。macOS 用户也需要获得新品牌 App。仅为 Logo 把两个已批准宠物包及 12,013 帧媒体重编为 `0.6.0`，会制造没有内容变化的伪版本和额外验收成本。
- Constraint: 已存在的 `v0.6.0` 标签不能移动；标签提交已经包含 Swift 宿主、Windows 宿主和最终 Logo；两个 `0.5.10` 宠物包必须保持 `runtime-chain-approved`、`installable=true` 和逐字节媒体身份；macOS 仍只支持 Apple 芯片与 macOS 14 及以上，使用 ad-hoc 签名且不公证。
- Decision: 本决策取代 ADR-041 中“Release 只有一个 Windows ZIP”的附件范围，不改变其 Windows 冻结产物与真机验收结论。v0.6.0 Release 精确提供 Windows ZIP 与 macOS DMG 两个附件。App 与平台发布版本为 `0.6.0`，内嵌宠物内容版本保持 `0.5.10`，双平台 schema 2 清单固定标签提交、平台、包 ID、包版本、Logo 哈希、附件字节数和 SHA-256。默认分支承载标签后的发布补充，两个验证流程先证明平台源码相对不可移动标签无变化。Windows Runner 在草稿阶段只复验 ZIP，macOS Runner 在公开后使用只读权限复验全部附件并挂载 DMG，最终发布动作与 CI 分离。
- Alternatives（否决）: 移动或重建 `v0.6.0` 标签；为版本号一致重新生成、抠图或重编宠物媒体；另发没有必要的 `v0.6.1` 只改 Logo；继续让 macOS 用户停留在旧 Logo；给 macOS 验证工作流持久写权限并允许自动发布。
- Tradeoff: 两个平台共享一个清晰版本入口，宠物内容身份保持真实，已有标签历史不被改写。代价是发布清单需要明确区分 App 和宠物包版本，标签后的发布补充必须从默认分支读取，并额外验证源码相对标签没有漂移。

## ADR-043 · 小型 Codex 双宠导出进入 Git 并保持独立批准边界 · 2026-08-19

- Problem: 五百与飞流已经各有一套可安装的 Codex v2 自定义宠物。如果只保存在 `~/.codex/pets`，它们不会随项目版本化、无法从远端恢复，也缺少统一哈希和安全安装路径；如果把它们混同为 PetsGraph 正式宠物包，又会错误继承连续视频、动作图和真实桌面批准结论。
- Constraint: 两张 WebP 合计约 4.4 MB，可以由普通 Git 承载；正式 PetsGraph 数百 MB 运行时媒体仍只进入 Release；五百和飞流形象遵守 `ASSETS.md`；机械图集校验不能代替 Codex 真实窗口人工观看；本地已有同名包不能被静默覆盖或删除。
- Decision: 在 `codex-pets/` 版本化保存 `wubai-v0` 与 `feiliu-hatch-native-v1` 的完整 `pet.json`、`spritesheet.webp` 和 schema 1 哈希清单。维护工具验证 v2 的 1536×2288、8×11、RGBA、目录白名单、字节数和 SHA-256，并安全安装到 Codex。相同包幂等跳过，不同包默认拒绝，显式强制替换前移动到 `pets-backups`。Codex 导出不进入 PetsGraph App、`.petsgraph-pet` 或 v0.6.0 Release，也不获得 `runtime-chain-approved`。
- Alternatives（否决）: 继续只维护在用户目录；把图集复制进 PetsGraph 正式包；把两张小图也放进 GitHub Release；使用 Git LFS；安装时直接覆盖同名目录；因为 Hatch Pet 机械校验通过就宣称动作视觉通过。
- Tradeoff: 普通 clone 增加约 4.4 MB，仓库需要维护另一套简单 manifest 和安装工具。换来两只 Codex 宠物可以被版本化、核验、恢复和共同维护，同时正式连续动作路线与其更低帧数的图集路线保持清晰隔离。
